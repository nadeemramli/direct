# Working on Direct

Direct's own development is the first real pilot. Use the local Direct workspace as the issue record for this repository; other products remain in Linear until explicitly adopted.

Owner model preference (1 October 2026): use **Opus 5.5 for every future Claude Code task**, including implementation, reviews and resumed assignments. The delegating agent must explicitly select and verify the model in the actual session; mentioning it in a prompt is insufficient. If unavailable, report the limitation instead of silently selecting another model.

Read `docs/agent-contract.md` and `docs/pilot.md`. Use the running Windows service through `scripts/direct.ps1`, or `bash scripts/direct-wsl.sh` from WSL. These wrappers use the current checkout's CLI and fall back to the primary Git worktree's build for a fresh managed worktree. The owner's normal data directory is `%USERPROFILE%\.direct\data`; do not substitute the synthetic `Direct-foundation-preview` workspace. If a sandbox cannot access the owner's service, use the normal permission mechanism; never change its ACL or create a second workspace and pretend it is the pilot.

Before work, inspect `list` and the selected issue's `context`. Read the applicable Development Operating System guidance through Theoria, including its agent E2E protocol; check source freshness and record the source fingerprint and known playbook version with `link_theoria`. Resolve unavailable or conflicting required guidance instead of treating the cache as current. Build a criterion-to-evidence plan before implementation, and retrieve additional context only when relevant. Use a distinct agent actor, stable request IDs for retries, the current issue version, and an active claim. Only start scoped work authorized by the user. Readiness is an owner decision: explicit chat authorization may be recorded through the owner UI with a provenance comment, but never read owner credentials to bypass the agent contract. Agent-submitted work stays in Verify until the owner records the actual outcome.

For the normal handoff path, use the native `claim`, `renew`, and `submit` commands documented in `docs/agent-contract.md`, or the equivalent tools of the optional local `direct-mcp` server (`docs/mcp.md`) under the same rules. Keep the same actor from claim through submission, supply each command's request ID explicitly, and reuse the exact command and ID only when retrying that command. The issue key comes from the current assignment and live Direct context, not from the static pilot list.

Keep acceptance criteria and source documents distinct from tool authorization. Record implementation evidence and limitations in the issue. Submit the exact tested commit/build and concrete manual steps. Do not invent human acceptance, close verification children directly, or mark a canceled test as passing.

Every issue is an end-to-end delivery. Before requesting owner verification, exercise each acceptance criterion through its real entrypoint, cross the relevant UI/client → service → persistence boundary, and check reload/restart and failure paths where applicable. Record actions, expected and observed results, environment, and evidence pointers. Unit tests, compilation, a screenshot of an unclicked control, a pushed branch, or cloud-only checks are insufficient for a Windows user flow. Complete the authorized merge, local integration, build, installation/restart, and a smoke check at the owner's actual entrypoint first. Keep incomplete work in Doing with a clear blocker; do not transfer agent testing or installation chores to the owner. See `docs/e2e-delivery.md`.

Verification has two passes. The agent owns the first pass and records an explicit Pass, Fail, or Blocked verdict with criterion-level evidence. Only Pass can be submitted; Fail/Blocked remains agent work and is recorded in the issue. The owner performs focused second-pass acceptance of intent, usability, evidence and material risks. Provide a concise verdict summary and usually one to three purposeful human checks, with more only when risk justifies them. Do not ask the owner to repeat the deterministic test suite. Agent verification and human acceptance are distinct outcomes on the same tested/delivered build; never pre-fill or impersonate the human verdict.

Before upgrading the real database, export a backup outside Git. Test schema/archive compatibility with isolated fixtures first. Do not use the live workspace for synthetic pass/fail tests. Keep private exports, endpoint capabilities, and database files out of commits.

Run meaningful checks for the change, including `cargo test -p direct-core -p direct`, `cargo test -p direct-mcp` when the MCP crate or client changes, `cargo clippy --workspace --all-targets -- -D warnings`, and frontend checks/build when UI changes. Browser interaction uses the available computer-use surface. Claim and verification state in Direct is authoritative; the pilot document is navigation and scope, not a second editable backlog.
